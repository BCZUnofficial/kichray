# G3a.1: полный охват кадра в диагностической телеметрии

G3a.1 продолжает G3a-S и меняет формат на `schema=2`. Причина: в четырёх
проверенных R4-снимках лимит 32768 событий исчерпывался преимущественно
отсечениями, отчёт заканчивался на тенях, а поздние `DETAIL_RENDERER` и
`MEMORY` терялись. Команда остаётся прежней: `d_snapshot 1`.

## Хранение и потери

Камера, заголовок, итоги проходов, агрегаты видимости и итог потерь хранятся
отдельно от подробных draw-записей. `DETAIL_RENDERER`, `MEMORY` и `SETTINGS`
имеют отдельные ограниченные хранилища. Для повторного ключа сохраняется
последнее значение. Отсутствие измерения обозначается явно; наличие раздела
само по себе не означает, что соответствующее измерение выполнено.

Для подробных draw-записей сохранён общий предел 8 МиБ / 32768 событий.
Бюджет распределён заранее, поэтому ранние тени не занимают место поздних
проходов:

| Группа проходов | Бюджет |
| --- | ---: |
| SUN_SHADOW | 2 МиБ |
| LOCAL_SHADOW | 2 МиБ |
| GBUFFER | 2 МиБ |
| FORWARD_TRANSPARENCY | 512 КиБ |
| LIGHT_ACCUMULATION, ENVIRONMENT_COMBINE, HUD_UI, POSTPROCESS, MENU_UI, OTHER | по 256 КиБ |

Известные имена R2 сопоставляются соответствующим группам. Неизвестные имена
делят `OTHER`. Неиспользованный бюджет одной группы не передаётся другой.
Сохранившиеся записи идут в исходном порядке. Общий размер файла может быть
больше 8 МиБ: ограниченные итоговые разделы находятся за пределами draw-буфера.

`TRACE_LOSS` и каждый `PASS` показывают наблюдавшиеся, сохранённые и потерянные
draw-записи, их байты, первую и последнюю потерю. Счётчики отправленных команд
продолжают обновляться после исчерпания бюджета. Потери приводят к
`INCOMPLETE`; охват всех проходов не означает сохранение каждой draw-записи.
Ошибки сериализации и переполнение хранилищ итогов отмечаются отдельно.
Байты не созданной из-за ошибки сериализации записи неизвестны.

Число агрегатов ограничено: 64 имени прохода, 512 групп проход/свет/фаза и
512 комбинаций видимости. При превышении используются явные группы `OTHER`,
ставится признак потери детализации; глобальные счётчики событий сохраняются.
У каждого агрегата видимости остаётся до четырёх примеров ресурсов.

## Что измеряется

- `VISIBILITY_SUMMARY`: проход, источник света, фаза/грань, тип и причина.
  `CANDIDATE_CLASSIFIED` означает инструментированную проверку с исходом
  `CULLED` или `SELECTED`; для таких проверок нули известны и
  `candidates = culled + selected`. Обычные `CANDIDATE` не объявляют полноту
  проверки. Счётчики относятся к наблюдениям, а не к уникальным объектам.
- `PASS_LIGHT`: реальные отправленные draw calls и треугольники отдельно от
  кандидатов. Выбор кандидата не равен успешной отправке и не доказывает
  видимые пиксели. Неинструментированные стадии остаются неизвестными.
- R4-свет имеет индекс в массиве текущего кадра и описание параметров.
  R2-свет может иметь `PROCESS_HANDLE`: такой ID нельзя сравнивать между
  запусками. Для теней указаны near/far либо локальная грань/фаза.
- `semantic_type` отделён от `render_queue`. Частицы определяются по
  `CParticleEffect`/типу визуала, glow — по реальному `R4Glow`. Эффект с
  неоднозначным типом не становится частицей по имени текстуры.
- Источники идентичности указаны в `semantic_evidence`: контейнеры и диапазоны
  `level.geom`, индекс detail-меша, определение частицы, исходные shader/texture
  names или хеш неизменной декодированной OGF-геометрии. Адрес GPU-буфера не
  выдаётся за стабильный ID меша. Неизвестные Release-источники обозначены явно.
  Форматы material ID R2 и R4 имеют разную область определения: равенство
  хешей не является условием визуального соответствия рендеров.
- До четырёх UV-пар с указанием источника. Это выборка реальных CPU-данных,
  а не полные вершины, UV-границы или GPU readback. CPU capture проверяет не
  более первых 32 ссылок индексов при выборе различных вершин; исходная
  выборка частицы сохраняется при отложенной отправке команды.
- `DETAIL_RENDERER`: Still/Wave1/Wave2, загруженные и активные меши, текущий,
  пустой или устаревший список экземпляров, ёмкость instance-буфера, реально
  загруженные байты, отдельные отправки геометрии/теней и legacy capture.
  `DETAIL_PASS` показывает повторы экземпляров в каждом теневом проходе.
  Тени используют список деталей, выбранный для камеры; отдельного отсечения
  экземпляров деталей по каждой тени этот патч не добавляет.
- `MEMORY`: CPU payload и capacity, выделенный instance-буфер и успешная
  загрузка, учтённый GPU payload реестра ресурсов. Эти значения не измеряют
  физическую резидентность VRAM и не являются общей памятью процесса.

Дополнительные данные команд capture выделяются только в запрошенном кадре;
хеш исходной OGF-геометрии вычисляется лениво и сохраняется у общего меша.
Структура `RenderSnapshotDraw` и ABI renderer DLL не изменены.

## Проверка на Windows

1. Пересобрать `XR_3DA`, R4 и эталонный `xrRender_R2` из одной версии исходников.
   EXE и R4 DLL должны иметь согласованные source/shader identity.
2. На проблемных местах с деталями, солнцем и огнём вызвать `d_snapshot 1`.
   Отдельно снять меню. Сохранять максимально одинаковые камеру, время и погоду
   для сравнения R2/R4.
3. Проверить `schema=2`, CAMERA, DETAIL_RENDERER, MEMORY, PASS, TRACE_LOSS и END.
   При переполнении должны оставаться итоги всего кадра и записи поздних
   активных проходов. Отсутствующий в кадре проход не обязан иметь draw-записи.
4. Проверить точные потери по проходам, равенства счётчиков и причины
   `INCOMPLETE`; не принимать сохранённую выборку за полную последовательность.
5. Проверить `legacy_detail_draws/vertices/indices=0` в R4, текущие instance
   counts, различие loaded/active meshes, повторные отправки в тенях,
   семантику огня/glow, UV и реальные состояния stencil/sampler.

Переносимые тесты используют production recorder и CPU-код с подменёнными
границами графического API. Они проверяют переполнение, поздние проходы,
обязательные итоги, ограничение числа ключей, сброс кадра, происхождение
частиц, IDs/UV, stale/menu detail-сводки и существующие контракты ресурсов.
Они не заменяют сборку MSVC и запуск на Windows/GPU.

G3a.1 меняет диагностические данные. Исправления stencil-контракта солнца и
sampler/UV-рендеринга частиц требуют следующего анализа полученных снимков.
