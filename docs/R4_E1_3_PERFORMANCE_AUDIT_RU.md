# R4 после E1.2: аудит производительности и границы следующего патча

Дата: 24 октября 2026 года. Это исходный аудит состояния E1.2, до изменений рендера. Реализованный объём E1.3 и границы проверки описаны в [R4_E1_3_RU.md](R4_E1_3_RU.md).

Главная обнаруженная проблема — стоимость формирования и отправки кадра растёт с числом теневых граней и числом объектов сцены. E1.2 восстановил участие источников света, но не обеспечил сопоставимый с R2 отбор работы. Бюджет памяти карт теней ограничивает память, а не число обходов сцены, команд рисования или время кадра. Это недоработка E1.2.

В первую очередь нужно исправлять отбор геометрии и света, повторную подготовку проходов и расходы отправки команд. Визуальные артефакты не входят в эту работу.

## 1. Основание и достоверность

Исследованы пять файлов `snap24.10.2026.13.37.32.log`, `13.38.18.log`, `13.39.24.log`, `13.40.27.log`, `13.41.45.log` и четыре сопровождающих скриншота. Все снимки R4/D3D11, 1920×1080; Кордон и Бар.

Проверен код ветки `feature/dx11-r4-bridge`:

- опубликованный E1.2: [89a9281dfcaf6a3c9b564c366dc2c399f98fdcd5](https://github.com/BCZUnofficial/kichray/commit/89a9281dfcaf6a3c9b564c366dc2c399f98fdcd5);
- локальный коммит: `423c47bb0506c28ba07134724a0e8cc60b349072`;
- одинаковое дерево исходников: `aaf15ad08b2cc55c266c4b5bed9bc472ecf45ddd`;
- референс X-Ray 1.6: [e162d87600976f6fecb00b0a0861a8ae6ea5758a](https://github.com/KaMeHb-UA/X-Ray-1.6/tree/e162d87600976f6fecb00b0a0861a8ae6ea5758a).

У логов идентификатор Git — `archive`. Хеш встроенного HLSL совпадает с E1.2 при учёте Windows CRLF. Это подтверждает соответствие шейдеров, но не заменяет привязку всего EXE к SHA коммита.

Суммарные draw-счётчики пригодны для оценки объёма работы: `draw_aggregate_observations_lost=0`. При этом подробная трасса и словари неполные. Их отсутствие нельзя трактовать как отсутствие объекта или операции.

В новом пакете нет обычного игрового журнала этой сборки с серией кадров без снэпшота и нет синхронного R2-бенчмарка. Поэтому аудит устанавливает лишнюю работу в коде, но не доказывает распределение обычного времени кадра между CPU, драйвером и GPU. Полная сборка MSVC и запуск игры здесь не выполнялись.

## 3. P0 — основные источники избыточной работы

### 3.1. Все выбранные тени строятся заново, без проверки полезности прохода

Код:

- `xr_3da/KichR4CaptureData.h:419–448`, `SelectLights`;
- `xr_3da/KichR4Visibility.h:73`, `SelectShadowLights`;
- `xr_3da/KichR4DeferredSession.h:34–49`, `PrepareLocalMaps`;
- `xr_3da/KichR4DeferredSession.h`, цикл `local_*_face_*`.

Отбор света учитывает активность, разрешение статических источников, яркость и сферу во фрустуме. Сортировка по важности не сокращает последующую работу. Для каждого источника с тенями выполняется один spot-проход либо шесть point-проходов с повторной отправкой static, моделей и деталей.

Пул повторно использует ресурсы depth textures. Содержимое теней не кешируется между кадрами. Привязка карт задаётся текущим индексом отсортированного источника, а не устойчивым source ID.

В снимке 13:41:45 запрошено 185 граней, выделена 191 карта 256×256, около 47,75 МиБ. Ограничение 64 МиБ соблюдено, однако число проходов осталось огромным.

В R2 и 1.6 есть проверка видимости источника, отдельный граф объектов в его подпространстве, проверка пустого графа и отбор теневых объектов. R4 воспроизводит лишь часть этого пути.

**Правка:** формировать список затеняющих объектов для источника/грани заранее; отбрасывать доказанно бесполезные проходы; добавить проверку видимости объёма влияния света. GPU-query должна быть асинхронной, с консервативным поведением при отсутствии актуального результата. Невидимость самой лампы не доказывает невидимость её света. Пустая грань должна иметь корректное состояние «полностью освещено», а не старую глубину.

Полное межкадровое кеширование depth-карт — отдельная возможность, но требует ключа source ID + generation + face + projection и корректной инвалидации по движению источника, объектов, скелета, ветру, alpha-материалу и разрешению. Цветовая пульсация без изменения геометрии не обязана инвалидировать глубину. Простое «обновлять каждую N-ю рамку» недопустимо для движущихся фонарей и теней NPC.

### 3.2. Видимость уровня вычисляется несколько раз для одного и того же прохода

Код:

- `xr_3da/KichR4TexturePreflight.h:30–89`;
- `xr_3da/KichR4LevelVisibility.h:36–57`;
- `xr_3da/KichR4DeferredSession.h:229–303`;
- `xr_3da/KichR4LevelCamera.h`, `Visible`.

Texture preflight самостоятельно вычисляет видимость для обеих солнечных карт и каждой локальной грани. Перед рисованием `Static` вычисляет её снова. Камерный отбор повторяется для прозрачной геометрии.

Каждый вызов создаёт новые массивы, обходит список геометрии, расширяет границы деревьев для ветра и проверяет AABB. Проход по порталам использует исходный фрустум без сужения через проёмы; HOM отсутствует. Он безопасен относительно потери геометрии, но не равнозначен отбору R2. Существующие узлы иерархии не служат пространственным ускорителем этого обхода.

**Правка:** один план кадра с результатами видимости и готовыми списками команд для камеры и каждого теневого вида. Эти же списки используют texture preflight и отправка. Границы с учётом ветра вычисляются один раз за кадр, плоскости — один раз на вид. Для уровня нужен пространственный отбор по иерархии/узлам с агрегированными границами, чтобы не проверять каждый leaf для каждой грани.

Теневой список должен сохранять объекты за камерой, которые отбрасывают тень на видимые поверхности. Подмена его камерным списком даст ошибочное ускорение.

### 3.3. Солнечный охват слишком грубый, детализация не адаптируется

Код:

- `xr_3da/KichR4LightingMath.h:40`, `SunShadow`;
- `xr_3da/KichR4DeferredSession.h:537–554`;
- `xr_3da/KichR4NativeRenderer.cpp:212–260, 287–298`;
- `xr_3da/KichR4LevelData.h:161–220`.

Две карты 2048×2048 используют охваты 128/512 м и глубину 1024 м. Охват задаётся от камеры, без полноценного построения объёма затеняющих объектов по видимым принимающим поверхностям, как у R2.

Дополнительно:
- `Submit` вызывает `v->Render(1.f)`;
- узлы `MT_LOD` раскрываются в дочернюю геометрию;
- загрузчик уровня сохраняет верхний SWI, а billboard-proxy не включается в выбор LOD.

Поэтому даже малозаметная геометрия может идти в несколько проходов с максимальной детализацией.

**Правка:** консервативный солнечный caster volume на основе видимых получателей тени, по принципу R2 `compute_caster_model`; сохранение и выбор существующих SWI/LOD по экранному размеру и размеру в карте тени. Учитывать объекты вне кадра, низкое солнце и движение камеры. Не уменьшать слепо фиксированные 512 м: это вернёт обрывы теней.

### 3.4. Слишком много моделей попадает в подготовку ещё до отсеивания по проходу

`KichR4NativeRenderer.cpp:274–302` собирает объединение камеры и всех теневых фрустумов. В последнем кадре — 186 теневых фрустумов. В помещении 13:39:24 камера даёт 69 источников моделей, тени добавляют ещё 369.

Уникальность renderable проверяется, но дорогая подготовка скелетов, материала, границ и экспозиции происходит для всего объединения. Уменьшение числа фактически рисуемых моделей в позднем backend не возвращает уже потраченное время.

**Правка:** сокращать ненужные виды и кандидатов до `renderable_Render/CalculateBones`; переиспользовать пространственные выборки и консервативные границы. Оптимизация должна начинаться до сборки команд, а не только перед `DrawIndexed`.

### 3.5. Подробная диагностика сама многократно усиливает задержку

Код: `KichR4DeferredSession.h:243–247`, `SnapshotStatic`, `SnapshotVisibility`; `RenderSnapshot.cpp`, `RenderSnapshot_Note`.

Метаданные static формируются до проверки результата отсечения для каждой грани. В последнем снимке зарегистрировано 914 729 кандидатов и 1 829 458 событий видимости. Ограничения трассы ограничивают сохранённый результат, но не весь расход на построение метаданных, строк и агрегатов.

`cpu_native_submit_ms` в этих снимках составляет примерно 3,1–29 секунд и явно включает телеметрию. GPU timestamp измеряет интервал между маркерами; при голодании очереди команд он может включать ожидание поступления работы с CPU. Его нельзя объявлять чистым временем занятости GPU.

**Правка:** дешёвые числовые счётчики для обычного профиля; словари один раз на ресурс/материал/эпоху; ограниченная детализация представителей с проверкой бюджета до дорогого форматирования. Сохранить точные суммарные счётчики и явно отмечать неполноту подробностей.

Это исправляет измерение и задержки снэпшота. Само по себе оно не объясняет и не устраняет всю просадку обычной игры.

Кеш state-объектов уже существует. Не хватает именно кеша текущих привязок. Его необходимо инвалидировать при смене прохода, reset/ClearState, внешнем изменении контекста и автоматическом снятии конфликтующих SRV/DSV. Иначе ускорение снова приведёт к неправильным текстурам и теням.

Для CB нельзя просто заменить `UpdateSubresource` на `Map` у старого DEFAULT-ресурса. Нужно изменить способ создания и обновления, сохранив контракт владения и совместимость с базовым DX11. Возможности DX11.1 и NO_OVERWRITE нельзя предполагать без проверки.

Палитры скелетов уже переиспользуются между проходами: в снимках 427–542 pose uploads, около 0,55–0,74 МиБ, не более одного upload на измеренный ключ. Ошибки повторной загрузки одного pose на каждую тень не подтверждены. Здесь приоритет — лишние кандидаты и количество операций, а не переход обратно к CPU skinning.

## 5. P2 — возможные отдельные фризы и проверенные альтернативы

**DDS и ввод-вывод.** `KichR4LevelSession.h` синхронно читает и загружает отсутствующий DDS при подготовке рабочего набора. Это возможный источник фризов при повороте камеры и переходе на уровень. `KichR4TexturePolicy.h` также содержит повторные линейные проходы при выборе mip/жертв.

Но в этих кадрах:
- DDS находится в пределах бюджета 384 МиБ: 336,1 / 354,4 / 383,6 / 251,8 / 383,9 МиБ;
- `dds_evictions_total`: 0 / 0 / 0 / 0 / 178;
- `dds_planned_mip_steps=0`, `dds_irreducible_budget_denials=0`;
- `mesh_uploads=0`, `cpu_expanded_model_vertex_bytes=0` во всех пяти снимках.

178 — накопленное число вытеснений, не «178 каждый кадр». По этим данным постоянный DDS churn не установлен. Утечку во всех сценариях пять снимков также не исключают. Новые счётчики должны разделять текущий кадр, интервал и время жизни.

Излишне широкий список теневых кандидатов может раздувать и texture preflight. Сначала сократить реальную потребность. Очередь фоновой подготовки DDS/ограничение upload-burst вводить по измеренным обычным фризам; увеличение бюджета не исправляет стоимость сцены. UI/HUD и корректные заглушки должны сохранять приоритет.

**Shader cost / fill-rate.** В R4 остаются аналитические material response, PCF и освещение через прямоугольные области вместо полного механизма light volumes/stencil 1.6. Это потенциальные GPU-расходы. Однако нынешние timestamps не показывают доминирования самого этапа накопления света: stage2 составляет около 0,2–3,5 мс в инструментированных кадрах. Переписывать материал или снижать разрешение первым действием оснований нет. Повторить оценку после разгрузки CPU.

**Синхронизация.** Постоянного forced-wait в чтении timestamp-query не найдено: используется DONOTFLUSH и отложенный опрос. `Flush` найден при reset/освобождении. CPU readback через staging/Map READ относится к пользовательскому скриншоту. Это не установленная причина постоянного слайд-шоу.

**Холодный запуск.** Создание shader/pipeline/буферов при первом использовании может дать отдельные задержки. Это нужно отличать от прогретого кадра. Нулевой mesh upload в пяти снимках не поддерживает гипотезу постоянной повторной загрузки мешей.

**Скрытое/свёрнутое окно.** Preflight в `KichR4NativePresenter.cpp:233–244` выполняется до определения suspended/occluded. Возможна лишняя работа в таком состоянии; к описанному игровому ракурсу это вторично.

**Память процесса.** Registered GPU payload 542–709 млн байт — сумма учтённых ресурсов, не замер занятой VRAM или доступного адресного пространства Win32. Нужны private bytes/working set и, где доступны, реальные DXGI budget/usage. Нельзя диагностировать переполнение VRAM по этой сумме.

`light_smapvis` кеширует сведения о видимости затеняющих объектов; это не готовое полное кеширование содержимого shadow maps. Atlas экономит размещение и переключения ресурсов, но сам по себе не убирает геометрию и повторный отбор. Эти механизмы нельзя выдавать за готовое решение всех 185 проходов.

## 7. Рекомендуемый объём E1.3 Performance

Патч должен менять подготовку и отправку кадра. Приоритетные изменения в порядке зависимости:

1. **Общий план кадра.** Единые списки camera/shadow, общий texture preflight, кеш границ, пространственный отбор статической геометрии и деталей. Очереди формируются по типу прохода; прозрачная очередь сортируется один раз.
2. **Сокращение теневой работы.** Отбор света по влиянию на видимую сцену, отдельные списки caster по граням, пропуск пустых проходов, консервативный солнечный объём. Сокращение фрустумов должно происходить до подготовки моделей.
3. **Существующие LOD/SWI.** Сохранить данные при загрузке и выбирать нужную детализацию; исключить безусловный `Render(1.f)` там, где поддерживается progressive LOD. Учитывать требования видимого и теневых проходов.
4. **Устранение повторных CPU/driver операций.** Кеш валидации неизменяемых mesh ranges, распределение ROS, фильтрация ForwardAdd/HUDAdd; dirty constants и кеш текущих DX11-привязок.
5. **Лёгкая проверяемая телеметрия.** Разделить selection/preflight/ROS/model preparation/submit/upload; считать реальные обходы, сортировки, shadow faces и изменения состояния. Ограничить стоимость detailed capture до построения строк.

Это связанный набор, но не однострочное исправление. Без пунктов 2–3 устранение повторных обходов ускорит CPU, однако оставит большую часть 6–15 тысяч теневых draw calls. Одно улучшение диагностики также не является решением обычного FPS.

Полное межкадровое кеширование карт теней и асинхронный DDS streaming следует добавлять после проверки перечисленных изменений, если обычный профиль показывает остаточный предел именно там. Они требуют самостоятельной проверки инвалидации и жизненного цикла. Произвольная квота света или пропуск актуальных теней не является критерием успеха.

## 8. Проверка готовности

Автоматические проверки перед сборкой:

- старый и новый отбор на контрольных сценах: ни один необходимый caster не потерян, в том числе за камерой и через второй вход/цикл порталов;
- неизвестные/неполные границы дают консервативный результат;
- одна visibility-выборка на уникальный вид, отсутствие повторной сортировки forward при росте числа ламп;
- валидация progressive диапазонов сохраняет защиту от выхода за vertex prefix;
- state cache проходит смены GBuffer/shadow/forward/HUD, alias SRV/DSV, reset и пересоздание device;
- фонари игрока/NPC, движущийся скелет, ветер и alpha-cutout сохраняют актуальную тень;
- DDS-план включает зависимости всех выбранных проходов и не возвращает UI debug fallback.

Игровая приёмка на Windows:

1. Одинаковое сохранение, время/погода, камера, разрешение и настройки; прогрев отдельно от измерения.
2. По 60–120 секунд R2 и R4: помещение → выход наружу → повороты в деревне → Бар с лампами → взгляд вниз/вверх → движение NPC и фонарь.
3. Закрытая консоль, обычный режим, без скриншотов и detailed snapshot во время измерения.
4. Сравнить медиану, p95/p99 frame time, длинные выбросы, 1% low, CPU preparation/submit и асинхронные GPU-этапы. Средний FPS отдельно недостаточен.
5. Проверить прогретую неподвижную сцену и повторы маршрута: нет постоянного создания одинаковых GPU-ресурсов, повторных mesh uploads и неограниченного роста памяти.

Уже доступны строки обычного игрового журнала `[R4 G3e frame]` и `[R4 G3e stability]` в `KichR4NativePresenter.cpp:312–324`. Их GPU-данные асинхронны и не соответствуют автоматически текущему CPU-кадру. Имеющееся окно 120 интервалов даёт грубую оценку 1% low; для окончательной оценки нужен более длинный ряд frame times.

Текущих материалов достаточно, чтобы начать перечисленные правки. Для подтверждения «работает так же ровно, как R2» нужен обычный журнал и сопоставимый игровой прогон, а не ещё одна тяжёлая подборка `d_snapshot`.
