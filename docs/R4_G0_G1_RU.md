# KichRay R4: G0–G1 — контракт и проверяемая база

Дата: 22.10.2026. База: `4274b7e389f720152c0cd795296db71244422908`.
Рабочая ветка: `feature/dx11-r4-bridge`. Цель совместимости: ТЧ 1.0006.

## Что изменилось

1. Добавлен единый экспорт `KichR4_GetRendererAPI`, ABI `0x00010000`.
   EXE получает одной операцией проверенный набор сервисов устройства, ресурсов,
   геометрии, DDS, потоков, графических проходов и служебных операций.
2. `KichR4NativePresenter.cpp` действительно использует этот контракт.
   Загрузка старой DLL, неправильные ABI/размеры/разрядность, отсутствующие
   функции и несовпадающие идентификаторы исходников диагностируются до
   создания D3D11-устройства. Частично заполненный контракт не публикуется.
3. Добавлены идентификаторы обеих частей комплекта: Git HEAD, состояние
   исходников, SHA256 исходников, SHA256 встроенного шейдерного заголовка,
   время компиляции, конфигурация, версия компилятора и размер указателя.
4. Генерация выполняется средствами MSBuild Visual Studio 2019/2022 через
   RoslynCodeTaskFactory. Не требуется устанавливать Python, CMake или Git.
   Для ZIP вместо Git HEAD выводится `archive`; проверка SHA256 остаётся.
5. Диагностика CPU-бюджета кадра содержит номер кадра, занятые/запрошенные/
   суммарные байты, предел, вершины/индексы, число команд, счётчики моделей/
   рук/UI, слой и источник резервирования. Для OGF сохраняется имя модели,
   для native draw — шейдер и текстура. Проверка суммы выполняется в 64 битах.
6. Добавлены тесты реального адаптера DLL и реального тела загрузчика EXE,
   C ABI, Win32 packing и диагностики переполнения. Исправлены устаревшие
   тестовые заглушки после появления native-пути B5.

Это основа G0–G1. Реализация маркируется `TRANSITIONAL`: существующая
CPU-сборка кадра, фиктивные D3D9-объекты и старые внутренние ABI пока остаются.
Новый экспорт объединяет работающие сервисы, не объявляет несуществующие
операции моделей и не добавляет второй набор GPU-ресурсов.

## Подтверждённая проблема Build 289

Все четыре предоставленных crash-лога заканчиваются цепочкой:

`Batch::Reserve` → `frame CPU geometry budget` → отказ `NativePresent` →
assert в `KichR4_NativePresentEngineFrame`.

Предел резервирования CPU-геометрии кадра — 32 МиБ. Он отличается от 74 МиБ
CPU-геометрии статического уровня и от ограничения количества lightmap-текстур.
Отрицательные веса 2W, отсутствующий `bind_wpn.script` и неподдержанные DDS
требуют отдельных проверок и сами по себе не доказывают причину этого отказа.
Файл `log_stable(20261021-223252).log` относится к тому же PID 27244, что и
один из вылетов, и не является отдельным успешным тестом стабильности.

Предел не увеличен; assert не подавлен; объекты при переполнении не скрываются.
Поэтому прежний вылет может повториться. Его корневая замена относится к G3:
постоянная GPU-геометрия, отдельные динамические потоки, передача экземпляров
и поз вместо общего CPU-кадра. Сам по себе успешный G1-handshake это не исправляет.

В G1 `NativeState::api` — единственный опубликованный EXE-снимок контракта.
`Context` хранит только дескрипторы и EXE-планировщики. Само GPU-устройство и
реестр GPU-ресурсов принадлежат DLL. Функции таблиц нельзя вызывать после
`FreeLibrary`. Создание/работа/уничтожение выполняются на потоке устройства.

Сцену сбрасывает `tools.reset_resources` между кадрами; операция сохраняет
устройство и swap chain. EXE одновременно заменяет `Context`, отбрасывая
старые GPU-дескрипторы. Итоговое уничтожение идёт через существующий
`geometry.destroy_device`, возвращающий общий отчёт. Наличие альтернативных
старых функций уничтожения не означает дополнительного владельца устройства.

Данные ABI — C-структуры pack(4), числовые дескрипторы, функции `__cdecl`.
STL, игровые классы и COM-указатели в новый контракт не передаются. Заимствованное
окно остаётся исключением платформенной интеграции: это непрозрачное значение,
его владение не передаётся DLL. Старые числовые соглашения blend/cull пока
сохранены внутри переходных таблиц; это не окончательный пакет команд модели.

Референс организации: `KaMeHb-UA/X-Ray-1.6`, ревизия
`e162d87600976f6fecb00b0a0861a8ae6ea5758a`, в частности
`src/Layers/xrRenderPC_R4/r4.h`, `src/Layers/xrRender/R_Backend.h`,
`src/Layers/xrRender/dxRenderFactory.cpp`. Его игровые форматы автоматически
не переносятся: форматная совместимость определяется исходниками ТЧ.

## Как считаются идентификаторы

`build/KichR4BuildIdentity.targets` перед `ClCompile` создаёт отдельный
`KichR4BuildIdentity.generated.h` в `IntDir` каждого из двух проектов.
Файл перезаписывается только при изменении содержимого. Параллельные проекты
не записывают в один общий заголовок.

`source_id` — SHA256 версионированного манифеста: относительные пути, длины
и SHA256 содержимого `.h/.cpp/.c/.inl/.def/.vcxproj` в `xr_3da` и `xrCore`,
а также двух файлов генератора в `build`. Сортировка — ordinal. Генерируемый
заголовок исключён. Пути корня, время файлов, документация, тесты, Git metadata
и результаты компиляции в манифест не входят. Рабочие копии с различными
байтами исходников, включая переводы строк, имеют разные `source_id`.

`shader_id` — SHA256 `KichR4DeferredShaders.h`, фактически используемого
встроенного набора HLSL. Это не хэш всего игрового `gamedata` и не checksum
машинного кода DXBC. Это также не SHA256 готового EXE/DLL: разные параметры
компиляции отражаются отдельно в конфигурации и версии компилятора.

Проверка совместимости требует валидных и одинаковых source/shader IDs.
Git revision/dirty, время, версия компилятора и конфигурация печатаются для
диагностики и отдельно не блокируют C-контракт. Поэтому одинаковые исходники
из ZIP и Git допустимы; перепутанная старая DLL получает понятный отказ.
Идентификатор зафиксирован при компиляции: исходники во время сборки не менять.

## Сборка и проверка в игре

1. Получить всю ветку `feature/dx11-r4-bridge`, включая новую папку `build`.
   При ZIP использовать новую папку исходников, не накладывать на старую копию.
2. Открыть `XR_3DA.sln` тем же Visual Studio и выбрать прежнюю рабочую
   конфигурацию Win32, не Dedicated. SDK/toolset этой правкой не меняются.
3. Пересобрать **XR_3DA** и **xrRender_R4**. Перенести **оба**:
   `XR_3DA.exe` и `xrRender_R4.dll`. При обычной полной пересборке решения
   использовать согласованный комплект остальных библиотек.
4. Для этой правки не нужны новые игровые шейдеры, изменение сохранений,
   новые ключи запуска или обновление `xrCore.dll`/`xrGame.dll` по причине G1.
5. Запуск R4 — прежний `-kich_r4_game`. В журнале должны появиться две строки
   `[R4 G0]` с идентификаторами EXE/DLL и `[R4 G1] renderer ABI=... verified`.
6. Проверить меню → загрузку Кордона → игру → меню → возврат в игру;
   изменение разрешения, сворачивание/восстановление и повторную загрузку.
   Проверить видео, линзу и порядок курсора: новых обещаний визуального
   исправления этот коммит не содержит, прежнее поведение должно сохраняться.
7. При вылете сохранить полный свежий stable/crash log. В строке budget
   должны быть `used_bytes`, `request_bytes`, `limit_bytes`, `layer`, `source`.
8. Отдельными запусками проверить R1/R2 без native-ключа. Они по-прежнему
   используют старую графическую реализацию и не загружают новый G1-контракт.

## Автоматические проверки

- `python tests/r4_native/run_tests.py`: реальный provider, реальное тело EXE
  loader, отказ на несовпадение/неполные таблицы, C ABI и x86 pack, точный
  бюджет, происхождение ошибки и MSBuild XML-связи.
- `python tests/r4_capture/run_tests.py`: OGF, CPU skinning, UI и capture.
- `python tests/r4_game/run_tests.py`: старый game runtime и DX9 presenter.
- `python tests/r4_frame/run_tests.py`: порядок операций кадра/очистки.
- `python tests/r4_deferred/run_tests.py`: проходы, свет, очистка и embedded HLSL.
- `python tests/r4_device/run_tests.py`: сравнение старых/новых DX9 lifecycle
  traces; требуется Git-объект базового master `6d832035`.
- `python tests/r4_capture/check_win32.py`: обновлён для нового provider,
  экспорта и компиляции native presenter; требует MinGW-w64.

Тестовый заголовок identity в `tests/r4_native` используется только тестами.
В production вместо него обязателен результат MSBuild. Изолированные тесты
не заменяют выполнение C#-задачи MSBuild, полный MSVC link и визуальную проверку
на Windows. Эти результаты следует фиксировать отдельно.
